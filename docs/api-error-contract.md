# API Error Contract

All API failures under `/api/v1` use the same JSON envelope:

```json
{
  "success": false,
  "error": {
    "message": "Human-readable message",
    "code": 400,
    "requestId": "request-correlation-id"
  }
}
```

## Status semantics

- `400` — malformed input, invalid identifiers, or validation failures
- `401` — missing/invalid/expired authentication
- `403` — authenticated but not authorized
- `404` — requested resource or API route does not exist
- `409` — duplicate/conflicting resource state
- `429` — rate limit exceeded; `Retry-After` is provided when available
- `503` — database/dependency temporarily unavailable
- `500` — unexpected server failure

Production responses never expose stack traces or internal exception details. The `requestId` can be supplied by the client through `X-Request-Id` or generated by the server and is returned in both the response header and error body.

Successful responses continue to use the existing `{ success: true, data: ... }` contract so existing frontend services remain compatible.
